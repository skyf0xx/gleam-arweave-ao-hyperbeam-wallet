AO transfer signing — status as of this session
=================================================

Goal: packages/core/src/ao/transfer.ts's submitTransfer() signs and sends an
AO Transfer message from a decrypted JWK, from the extension's background
service worker (no native Node APIs, Vite/WXT + vite-plugin-node-polyfills).

Fixed this session (real bugs, keep these):
- aoconnect's default browser export condition (dist/browser.js) only
  supports an injected-wallet signer, not a raw JWK. Fix: import
  "@permaweb/aoconnect/browser" explicitly and hand-roll a signer instead
  of using createDataItemSigner.
- The signer now matches aoconnect's own non-passthrough (create, format)
  contract: create({publicKey, type, alg}) returns the ANS-104 deep hash
  to sign; we sign it via @dha-team/arbundles/web's ArweaveSigner (backed
  by arweave/web's WebCrypto driver) and return {signature, address}
  (address = SHA-256 of the raw public key, not the public key itself —
  got this wrong on the first pass, fixed).
- Removed the old wxt.config.ts aliasing of @permaweb/aoconnect /
  @permaweb/ao-core-libs to their Node builds, and the Buffer
  "base64url"-encoding monkeypatch that hack required — neither needed
  anymore since we no longer force those packages' Node builds into the
  service worker.
- Added a normalizeJwkBase64Url() pass in buildJwkSigner (re-encodes
  n/e/d/p/q/dp/dq/qi to strict unpadded base64url) as a defensive
  guard before constructing ArweaveSigner.

Current blocking error:
  "The JWK member 'n' could not be base64url decoded or contained padding"
  — thrown by Chrome's native crypto.subtle.importKey("jwk", ...) inside
  arweave/web's WebCryptoDriver.sign(), called from ArweaveSigner.sign()
  in buildJwkSigner.

What's been ruled out (verified clean by tracing the full call chain,
generation -> storage -> decryption -> message-passing -> signer):
- JWK generation (packages/core/src/keys/jwk.ts) is a bare passthrough of
  arweave-js's wallets.generate() — native WebCrypto export, guaranteed
  correct base64url.
- Vault encryption/decryption (packages/core/src/vault/envelope.ts) only
  ever touches opaque ciphertext/salt/iv bytes, never jwk.n itself.
- JSON.stringify/parse round-trips at encrypt input / decrypt output are
  byte-exact for the string.
- The chrome.runtime message-passing boundary (popup -> background) never
  carries the JWK at all — only walletId/recipient/amount. The JWK is
  looked up entirely inside the background worker via key-session.ts's
  chrome.storage.session read, which is a plain JSON passthrough (no
  structured-clone weirdness, no class wrapper/Proxy).
- No Zod schema touches jwk.n anywhere in this codebase.
- normalizeJwkBase64Url itself is correct in isolation (tested the regex
  standalone) but did NOT fix the real-device error — meaning either the
  key was already valid before normalization (likely, given the trace
  above) and the failure is happening for some other reason inside
  arweave/web's WebCryptoDriver / Chrome's importKey call, or the stored
  key for the wallet under test is itself corrupted at rest from before
  this session's fixes (never confirmed either way).

Not yet tried / where to pick this up next:
1. Add a temporary console.log(JSON.stringify(jwk.n), jwk.n.length) right
   before the crypto.subtle.importKey call in
   node_modules/arweave/web/lib/crypto/webcrypto-driver.js (or add an
   equivalent log in buildJwkSigner right before `new ArweaveSigner(jwk)`)
   and capture the ACTUAL string from a real failing send — every other
   diagnostic step so far has been static tracing/reconstruction, not a
   captured value from the real failure. This is the fastest way to know
   definitively whether n is malformed at that point or not.
2. Test with a freshly generated wallet (not the one that's been failing)
   to rule out a corrupted-at-rest key from before this session's fixes —
   if a fresh wallet works, the old key is just bad and needs
   regenerating/re-importing, not a code fix.
3. If a fresh wallet still fails: the two remaining untraced spots are
   packages/core/src/arweave/transfer.ts (the AR send path — if it also
   fails the same way, the bug is upstream of ao/transfer.ts entirely,
   in wallet storage/generation, contradicting the "clean" trace above
   and worth re-checking) and packages/core/src/models/wallet.ts (not
   yet read this session).
4. Double check whether ArweaveSigner's constructor (jwkTopem(jwk) from
   arweave/node/lib/crypto/pem.js — note: NODE path, imported by the WEB
   build of @dha-team/arbundles, which is unusual) does its own
   byte-level reprocessing of jwk.n via ASN.1/PEM conversion that could
   silently produce a bad key even when the input jwk.n was fine. This
   was flagged as a lead but never actually inspected line-by-line.
