## Notes

No critical or high finding.

What the review checked and found sound:

- **Caller tiers.**
  - A dApp message in the mobile app dispatches only as `contentScript`. The origin comes from native for the frame that sent it: `addWebMessageListener`'s `sourceOrigin` on Android, `frameInfo.securityOrigin` on iOS.
  - `attestedOrigin` drops anything that isn't a main frame with an exact http(s) origin.
  - The wallet UI is the only extension-tier caller.
  - The worker host and every other comlink endpoint use `exposeMethods`.
- **Replies.**
  - Native delivers a reply only if the page's `location.origin` still equals the target at delivery time.
  - A cross-origin navigation gets a new tab id.
  - Android avoids `JavaScriptReplyProxy`.
- **Isolation.**
  - The dApp view has its own profile (Android `gleam-dapp`, needing `MULTI_PROFILE`) or data store (iOS), and no Capacitor bridge.
  - No `addJavascriptInterface`.
  - File and content access are off, and `file:`, `javascript:` and `content:` navigations are blocked.
  - `intent:` URLs keep only data and package and need a prompt.
  - TLS errors cancel, mixed content is never allowed, and there is no cleartext.
  - Web inspection is debug-only.
- **Keys on mobile.** Unlocked keys are non-extractable `CryptoKey`s in the worker's memory only. SQLite holds the sealed vault and `local:` data, outside iCloud and device backups. Android disallows backup and device transfer.
- **Biometric unlock.**
  - The vault password is held in the Keychain with `biometryCurrentSet` and `WhenPasscodeSetThisDeviceOnly`, with no passcode fallback.
  - On Android it sits behind a Keystore key with `BIOMETRIC_STRONG`, invalidated on enrolment.
  - A stored password that `probeVaultPassword` says no longer opens the vault is removed.
- **Approval sheet.** Going to the background rejects every open approval, and so does a lock. One request shows at a time, keyed by id. The origin shown is the runtime's stored copy.
- **Points links.** Only `https://open.gleamwallet.app/invite` and `/attest` are accepted, strictly parsed. An attestation goes through the site tier and needs the normal approval.
- **Watch wallets.** They hold no key material and can't connect or sign. An existing grant can't reach one, because the refusal is checked on every provider call while one is active.
- **Ledger data items.** Turning on `signDataItem` only changes which payloads reach the device. The background verifies every signature against the wallet's key, and the Permaweb app shows the item on the device.

On the accepted findings:

- **F-5:** the user still has to tap Open, and the prompt names the site.
- **F-6:** the sheet still needs an explicit approval and shows a decoded preview.
- **F-7:** the native view sits above the sheet, so it would take the tap.
- **F-8:** it is referral gaming with no signing (the same as the desktop site message).
- **F-9:** `harden-runner` doesn't support macOS runners on the community tier.
- **F-10:** `verify.mjs` fails the `open.gleamwallet.app` deploy until the fingerprints are set, so nothing broken ships.

The mobile app was reviewed from source only. Nothing native was built or run for this audit. The Swift change is compiled by the CodeQL Swift job.
