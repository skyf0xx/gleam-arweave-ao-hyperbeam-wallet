## Notes

No critical, high or medium finding. What the review checked and found sound:

- **Page to wallet.** A site message reaches a handler only if `sender.origin` is `SITE_ORIGIN` and it matches a strict schema. The handler re-parses the attestation, so only known keys, bounded lengths and printable text reach the approval window. The window opens from the extension, never from page-supplied UI. A page that can message the extension still needs the user to approve in that window, and the thing signed is `gleam-points:attest:v1:<release>:<sha256>` over the parsed attestation. It signs no transaction and moves no funds.
- **Signature binding.** The server recomputes the id from the parsed attestation, requires the signed message to equal `buildAttestMessage(release, id)`, then verifies the proof. A signature for one attestation does not verify for another.
- **State changes.** Submission takes a per-release advisory lock, locks the wallet row `FOR SHARE` and the challenge row `FOR UPDATE`, and re-checks used challenge, one scan per wallet and the paid-place count inside the transaction. A lost-response retry returns the original result.
- **Challenge.** Functions are drawn with rejection sampling from a random 32-byte seed, from the surface files at the release tag's commit read from GitHub. A challenge is unexpired, unused, and bound to the latest release and the tag's current commit.
- **GitHub reads.** Only the configured repo is contacted, and releases and commits are validated before use. A token goes to `api.github.com` only. Responses are size-capped and cached, and failures are cached for a minute.
- **CLI.** Git is called with an argument array, so no shell is involved. Paths from the challenge or attestation go through `git show <commit>:<path>` as one argument. Backup file names are restricted to `[A-Za-z0-9_-]`. The CLI never holds a key.

F-1 is a coverage gap in the audit process, not a bug in a path. It stays open and is recorded in `todo.md`. Fixing it edits `security/surface.txt`, a surface file. If that lands before v1.27.0 is tagged, the gate fails until this audit's `commit` is moved past it; otherwise it goes into the next release's audit.

F-3 and F-4 are the limits SCANS.md already states ("limited payoff"; the payoff is small and fixed per scan). A maintainer can void a scan with `scan-void`.

This was one reviewer's read, not a second pair of eyes. The "Not read" list above is real work left, and the whole surface outside the scan paths still wants a full audit pass before it can be called reviewed.
