# @gleam/extension

The Chrome MV3 extension itself: the WXT build that turns `packages/core`,
`packages/messaging`, and `packages/ui` into the installable wallet. It
owns every browser-specific concern — the manifest, the background
service worker, the content script and injected page provider, and all
the popup/sidepanel/approval UI.

Everything here is a caller or an adapter. Signing, balances, transfers,
and uploads live in `@gleam/core`; this package wires that domain logic
to Chrome APIs and to the page.

## Components

- [`wxt.config.ts`](#wxtconfigts) — manifest and build config
- [`entrypoints/background`](#entrypointsbackground) — the service worker
- [`entrypoints/content`](#entrypointscontent) — the isolated-world relay
- [`entrypoints/provider`](#entrypointsprovider) — the injected `window.arweaveWallet`
- [`entrypoints/approval`](#entrypointsapproval) — the signing/connect approval window
- [`entrypoints/passkey`](#entrypointspasskey) — the WebAuthn ceremony window
- [`entrypoints/connect` / `entrypoints/keyring`](#entrypointsconnect--entrypointskeyring) — hardware wallet support
- [`entrypoints/sidepanel` / `entrypoints/popup/*`](#entrypointssidepanel--entrypointspopup) — the main wallet UI
- [`src/dispatch/methods.ts`](#srcdispatchmethodsts) — the privilege table
- [`src/handlers/`](#srchandlers) — background use-case logic
- [`src/adapters/`](#srcadapters) — `@gleam/core` port implementations
- [`src/App.tsx`](#srcapptsx) — the shared UI shell

### `wxt.config.ts`

The MV3 manifest, generated by WXT. Declares permissions (`storage`,
`sidePanel`, `tabs`, `alarms`, `offscreen`, `idle`), static
`host_permissions` built from `@gleam/core`'s default gateway and
HyperBEAM peer lists, and `optional_host_permissions: ["https://*/*"]`
so a user can add a custom HyperBEAM peer without a wider install-time
permission. `externally_connectable` is scoped to
`https://gleamwallet.app/*` only, for the site's invite code and scan
attestation messages. `provider.js` is served as a
web-accessible resource with a dynamic URL, so a page can't fingerprint
the extension by probing for a fixed resource path.

### `entrypoints/background`

The MV3 service worker (`index.ts`) and the extension's only privileged
process. It builds every adapter and handler, registers each
`ProtocolMap` method from `@gleam/messaging`, and is the single place
that enforces `src/dispatch/methods.ts`'s privilege table before a
handler runs. It also owns alarms (auto-lock, activity promotion, the
points heartbeat), idle-lock, and pushing provider events to open tabs.

### `entrypoints/content`

Runs at `document_start` in the page's isolated world, top frame only.
It injects `provider.js` into the page and relays messages both ways:
a `PageRequestEnvelope` from the page becomes a `providerCall` message
to the background; a response or pushed event comes back as a
`PageResponseEnvelope`. It never reads or sets the request's origin —
the background derives that itself from the trusted Chrome sender, so
a page can't spoof which site is asking.

### `entrypoints/provider`

Built into `provider.js` and injected into the page's own world. It
installs `window.arweaveWallet` (`GleamProvider`) and `window.gleam`,
turning each call into a `postMessage` round trip to the content
script with a timeout. It also detects whether another wallet (Wander,
PermawebOS) is installed and defers to it unless the user has chosen
Gleam for that site.

### `entrypoints/approval`

A standalone popup window opened by `ApprovalHandler`
(`src/handlers/approval.ts`) whenever a page's request needs a
decision: connect, sign, encrypt, decrypt, or add a token. Its screens
(`ConnectionRequestScreen`, `SigningApprovalScreen`, `AddTokenScreen`)
show a decoded preview of what's being signed. Hardware-wallet flows
route through `AwaitingDeviceView` and the Keystone/Ledger panels here
too. Closing the window without acting counts as a rejection.

### `entrypoints/passkey`

Its own popup window, opened by `src/passkey/open-window.ts`. WebAuthn
ceremonies need this because the extension's action popup closes the
moment the browser's passkey prompt takes focus — so from the action
popup, every passkey ceremony is handed off to this window instead.
The side panel and approval window run the ceremony inline, since they
don't have that focus problem.

### `entrypoints/connect` / `entrypoints/keyring`

`connect` hosts the hardware-wallet connection UI (Ledger/Keystone).
`keyring` is an offscreen document — invisible, but alive as long as
the background needs it — that holds unlocked signing keys as
non-extractable `CryptoKey`s in memory. `src/adapters/offscreen-keyring.ts`
and `session-key-store.ts` are how the background talks to it; nothing
outside that pair reaches into the offscreen document directly.

### `entrypoints/sidepanel` / `entrypoints/popup/*`

The main wallet UI. The side panel and every popup screen (onboarding,
unlock, send, receive, activity, collectibles, connected apps,
contacts, settings, points, and the rest) mount the same shared shell,
`src/App.tsx`, which owns top-level view state across all of them.

### `src/dispatch/methods.ts`

The privilege table the background consults before running any
method. Every `ProtocolMap` method is tiered as `extension`,
`contentScript`, or `page`. Page-tier methods (the `window.arweaveWallet`
surface) each declare whether they need an approval, whether they need
an existing grant, and the Zod schema their params are parsed with.
`SITE_MESSAGES` lists the `site` tier: what the Gleam site's pages send
over `externally_connectable`, which no dApp page can reach.
`src/dispatch/site.ts` is the one entry point for those messages: it
checks Chrome's `sender.origin` and the message's schema before any
handler runs.
This is the one place that decides what a page is allowed to ask for —
no handler re-checks it.

### `src/handlers/`

One file per use case, each holding the logic a background message
maps to. Handlers depend only on ports (`StoragePort`, `ApprovalPresenterPort`,
etc.), never on `chrome.*` directly.

- **`wallet-lifecycle.ts`** — create, import, lock/unlock, rename, delete, and switch wallets.
- **`reads.ts`** — balances, token balances (AO, watched, and discovered from the wallet's history, minus hidden ones), token metadata and routing, activity, prices, network settings.
- **`transfer.ts`** — AR/AO transfer estimate and submission. A token on `arweave-scheduler@1.0` is sent as an L1 transaction, a legacy token through the MU.
- **`upload.ts`** — ANS-104 upload review and submission.
- **`approval.ts`** — the connect/sign/encrypt/decrypt/add-token/scan-attestation approval lifecycle, including opening and tracking approval windows.
- **`key-session.ts`** — reads the unlocked signer from `chrome.storage.session` and enforces auto-lock.
- **`provider-params.ts`** — decodes and validates the wire params for every `window.arweaveWallet` method.
- **`announcements.ts`, `contacts.ts`, `points.ts`, `security-phrase.ts`, `site-wallet.ts`, `passkey.ts`** — one handler each for their named feature. `points.ts` also signs and submits scan attestations, and `attest-errors.ts` words the points API's refusals for the person signing.

`src/points-invite.ts` and `src/points-attest.ts` handle the site's
messages once `dispatch/site.ts` has checked them, handing off to
`points.ts` or `approval.ts`.

### `src/adapters/`

The implementations of `@gleam/core`'s ports for this extension. Core
never imports Chrome APIs directly — it only knows about these
interfaces.

- **`storage.ts`** → `StoragePort` over WXT storage.
- **`windows.ts`** (`WindowApprovalPresenter`) → `ApprovalPresenterPort`, opens and tracks one approval window per request id so a restarted service worker can still find them.
- **`runtime.ts`** → `RuntimePort` over `@webext-core/messaging`.
- **`session-key-store.ts` / `offscreen-keyring.ts`** → bridge to the offscreen keyring document.
- **`badge.ts`, `downloads.ts`, `device-key.ts`** → the action badge, file downloads, and the Gleam Points device keypair.

### `src/App.tsx`

The shared UI shell mounted by the side panel, every popup screen, and
the approval/passkey windows. It drives top-level view state so each
surface doesn't reimplement its own routing.

## Data flow

A page talking to the wallet never reaches the background directly —
it goes through three hops, each a privilege boundary:

```
page (window.arweaveWallet) → content script → background → handler → @gleam/core
```

1. **Page → content script.** `GleamProvider.sign()` (or any other
   provider method) posts a message to itself; the content script,
   living in the isolated world of the same tab, is the only listener
   that can act on it.
2. **Content script → background.** The content script forwards the
   call as a `providerCall` message. It attaches no origin — the
   background reads the real origin from Chrome's `sender`, so the
   page can't lie about which site is asking.
3. **Background enforcement.** The background looks up the method in
   `src/dispatch/methods.ts`, validates params against its Zod schema,
   and checks whether an active grant already covers the request. If
   the method needs approval, it opens an `entrypoints/approval`
   window and waits for the user's decision before continuing.
4. **Handler → core.** Once allowed, the matching `src/handlers/*`
   function runs, using `key-session.ts` to get the unlocked signer and
   calling into `@gleam/core` (for example `core/ao/transfer.ts` or
   `core/arweave/transfer.ts`) to actually build, sign, and submit.
5. **Response flows back** through the same three hops in reverse: the
   background replies to the content script, which posts the result
   back into the page, resolving the original `window.arweaveWallet`
   promise.

The popup, side panel, and approval UIs skip steps 1–2 — they're
already extension-tier, so they call background handlers directly over
`@webext-core/messaging`. Only page-originated calls go through the
content-script relay and the approval/grant check.
